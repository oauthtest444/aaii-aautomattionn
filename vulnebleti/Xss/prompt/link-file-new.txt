## 6. Source-to-sink tracing

A regex match is **not automatically a vulnerability**.

For every relevant match, manually trace the value through the JavaScript.

Determine:

* Original attacker-controlled source.
* Variables receiving the value.
* Functions through which the value passes.
* Transformations performed on it.
* URL parsing.
* Decoding/encoding.
* Sanitization.
* Validation.
* Filtering.
* Allowlisting/blocklisting.
* Type conversions.
* String concatenation.
* Object/property access.
* Cross-function propagation.
* Cross-module propagation where possible.
* Final security-sensitive sink.

Determine whether attacker-controlled input can actually reach the sink.

Classify every result as:

* **Confirmed vulnerability**
* **Likely vulnerability / requires additional verification**
* **Safe / false positive**

Do not report a vulnerability based solely on a regex match.

This is extremely important.

The JavaScript URLs were collected by manually visiting each route individually.

Therefore:

**Treat every route → JS URL mapping in `routes-and-js-urls.txt` as authoritative.**

For each finding, identify the route(s) for which the relevant JavaScript was loaded.


## 9. Exploitability verification

For each potential vulnerability, determine:

1. Can an attacker control the source?
2. What exact input is controllable?
3. Where does the input enter the application?
4. Can the attacker influence the relevant variable?
5. Does the value survive validation/sanitization?
6. Does it reach the security-sensitive sink?
7. Is the vulnerable code actually executed on the relevant route?
8. Are there browser/API restrictions?
9. Are there authentication requirements?
10. Does exploitation require an attacker-controlled webpage, link, iframe, account, or other capability?
11. Is user interaction required?
12. Is exploitation same-origin or cross-origin?
13. What is the realistic security impact?

Do not overstate impact.
